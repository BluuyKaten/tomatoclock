# 番茄钟 App 开发前置文档（Final v1.1）

> 版本：v1.1 · 2026-08-04 · 作者：Claude 1（产品&架构）  
> 定位：跨平台桌面端番茄钟，专注计时 + 多模态分心检测 + 学习记录与分析 + 离线优先  
> **v1.1 更新**：UI 框架由 Dioxus 0.8 切换为 **Tauri 2 + Web 前端**，补充迁移路线图

## 1. 需求概述、业务目标、用户场景

### 1.1 需求概述
一款以 **Rust** 实现的跨平台番茄钟应用，面向**在校大学生与上班族**，提供：
- **番茄计时**（可自定义专注/休息时长）
- **多模态分心检测**（活跃窗口 + 输入空闲 + 摄像头视线/人脸）
- **渐进式提醒**（桌面通知 → 声音 → 语音 → 浮窗强提醒）
- **学习记录**（文本/图片/标签/科目/关联番茄时段）
- **数据统计与习惯分析**（规则型 + 可选 LLM 总结）
- **离线优先 + 账号体系**（离线可用番茄钟，联网启用同步/LLM）

当前阶段：**Windows 初始版本**；未来扩展至 macOS / Linux / 移动端。

### 1.2 业务目标
1. 通过番茄工作法降低启动阻力，帮助用户建立可持续专注习惯。
2. 量化专注质量：不仅记录"学了多久"，还记录"是否真正专注"。
3. 提供可执行的复盘：从数据中提炼学习问题与改进建议。
4. 隐私优先：摄像头/窗口数据默认本地处理，敏感权限显式授权。
5. 渐进式能力：离线核心功能可用，联网解锁同步与 LLM 增值能力。

### 1.3 用户场景

| 编号 | 场景 | 描述 |
|---|---|---|
| S1 | 开始专注 | 用户选择任务/科目，点击"开始 25 分钟番茄"，计时托盘常驻。 |
| S2 | 多模态分心监控 | 后台同时检测：① 活跃窗口是否在白名单 ② 鼠标键盘是否长时间无输入 ③ 摄像头中人脸/视线是否离开。 |
| S3 | 渐进式提醒 | 分心发生：托盘闪烁（1 级）→ 桌面通知（2 级）→ 提示音 + 语音"请回到学习"（3 级）→ 浮窗强提醒（4 级）。 |
| S4 | 番茄结束 | 记录本次番茄（时长、是否打断、分心次数、分心应用分布），提示休息。 |
| S5 | 学习记录 | 用户在番茄中/后写笔记，可贴图片、打标签、关联科目与具体番茄时段。 |
| S6 | 日/周/月复盘 | 查看专注时长趋势、分心高频时段、高频分心应用、科目分布热力图。 |
| S7 | 规则型问题总结 | App 本地生成"本周学习问题清单"（如"下午 2-4 点分心率 42%"、"数学连续 4 天未复习"）。 |
| S8 | LLM 深度复盘 | 用户授权后，调用 Claude API 生成更自然的学习复盘与改进建议。 |
| S9 | 离线使用 | 无网络时，番茄钟、分心检测、本地记录、规则分析全部可用。 |
| S10 | 多端同步（V2） | 用户在电脑与手机间同步番茄记录、笔记、配置。 |

## 3. 非功能性需求

| 维度 | 要求 | 说明 |
|---|---|---|
| **性能 - 内存** | ≤ 80 MB（不含摄像头推理）；摄像头开启时 ≤ 150 MB | 常驻后台必须轻量 |
| **性能 - CPU** | 空闲 < 1%；检测时 < 5%；摄像头推理时 < 15% | 避免影响用户工作 |
| **启动速度** | 冷启动 ≤ 1s | 用户可能频繁开关 |
| **计时精度** | 误差 ≤ 500ms | 使用单调时钟 `Instant` |
| **分心判定延迟** | 从发生到判定 ≤ 2s | 实时性影响提醒效果 |
| **并发** | 单用户本地，无高并发需求；异步事件驱动即可 | 数据量小 |
| **扩展性** | 检测器/提醒器/分析器插件化（Rust trait 抽象） | 便于 V2 扩展 |
| **可用性 - 离线** | 无网络时 M1–M10 全部可用 | 核心卖点 |
| **稳定性** | 崩溃率 < 0.1%；检测模块异常时降级为纯计时器 | 故障隔离 |
| **隐私** | 摄像头/窗口数据本地处理，不上传；敏感权限显式授权 | 用户信任基石 |
| **跨平台** | Windows（V1）→ macOS / Linux（V1.1）→ 移动（V2） | 平台相关代码隔离 |
| **可维护性** | 模块边界清晰；核心逻辑纯函数便于单测 | Rust 类型系统辅助 |
| **可观测性** | 结构化日志（tracing），关键事件埋点便于复盘 | 便于排查检测问题 |

## 4. 技术选型方案

### 4.1 整体选型

| 层 | 选型 | 理由 |
|---|---|---|
| **语言** | **Rust**（用户指定） | 内存安全、高性能、跨平台编译、适合常驻后台 |
| **UI 框架** | **Tauri 2**（Rust 后端 + 轻量 Web 前端） | 系统托盘/通知/浮窗生态成熟、跨平台一致、前端灵活；原用 Dioxus 0.8，因系统能力生态不足而切换 |
| **前端（Tauri WebView 内）** | **Svelte 5 / Vanilla TS** | 轻量、启动快，避免 React 重运行时；Svelte 适合桌面小工具 |
| **前端与后端通信** | **Tauri Command（invoke） + Event** | Rust 暴露 `#[tauri::command]`，前端通过 `invoke` 调用；后端推送事件用 `emit` |
| **存储 - 结构化** | **SQLite（rusqlite + migrations）** | 嵌入式、零配置、单文件、适合个人量级 |
| **存储 - 文件** | **本地文件系统**（图片/缓存） | 图片存本地路径，数据库只存引用 |
| **异步运行时** | **tokio** | Rust 异步事实标准 |
| **窗口检测** | **active-win-rs** | 跨平台活跃窗口抽象 |
| **输入检测** | **rdev** / **device_state** | 跨平台鼠标键盘事件 |
| **摄像头推理** | **ONNX Runtime（ort）** + **人脸/视线模型**（本地） | 纯本地推理，不上传；模型可选轻量（如 MediaPipe/YOLO-nano） |
| **系统通知** | **tauri-plugin-notification** | 跨平台通知 |
| **系统托盘** | **tauri-plugin-tray** 或 **tray-icon** | 托盘常驻 |
| **语音提醒** | **系统 TTS**（Windows SAPI / macOS say） | 无需额外模型 |
| **序列化** | **serde + serde_json** | 记录/配置持久化 |
| **日志** | **tracing + tracing-subscriber** | 结构化日志 |
| **LLM 调用** | **Claude API（claude-axon 或原生 HTTP）** | 用户接受联网 + API 费用 |
| **打包** | **tauri-bundler** | 一键出各平台安装包 |

### 4.2 为什么从 Dioxus 0.8 切换到 Tauri 2？

原方案使用 Dioxus 0.8（纯 Rust UI），切换原因：

| 能力需求 | Dioxus 0.8 | Tauri 2 |
|---|---|---|
| 系统托盘常驻 | 社区方案不成熟 | 官方 `tauri-plugin-tray` ✅ |
| 桌面通知 | 需自行封装 Win32 | 官方 `tauri-plugin-notification` ✅ |
| 浮窗/多窗口置顶 | 支持但生态弱 | 成熟，配置化 ✅ |
| 全局快捷键 | 需自行封装 | 官方 `tauri-plugin-global-shortcut` ✅ |
| 窗口管理（置顶/穿透） | 需自行封装 | `WebviewWindow` 配置化 ✅ |
| 未来多端同步 | 需自建 | 前端可复用为 Web 端 ✅ |

**结论**：番茄钟强依赖系统级能力，Tauri 2 生态显著优于 Dioxus，切换可降低长期维护成本。

### 4.3 前端选型说明

**为什么选 Svelte 5 / Vanilla TS 而非 React？**
- 番茄钟是轻量工具，React 运行时偏重。
- Svelte 5 编译后体积小、启动快，适合桌面小工具。
- 若团队熟悉 React，也可接受，但建议优先 Svelte。

### 4.4 关键选型说明

**为什么选 Tauri 2 而非纯 Rust GUI（egui/iced）？**
- 番茄钟需要**系统托盘、通知、浮窗**，Tauri 生态更成熟。
- 未来多端同步后，Web 前端可复用为 Web 端。
- 开发效率高，UI 调整灵活。

**为什么摄像头推理选 ONNX 本地模型？**
- 隐私优先：用户敏感，不能上传视频流。
- 离线可用：无网时仍能检测。
- Rust 生态 `ort` crate 已成熟。

**为什么存储选 SQLite 而非纯文件？**
- 需要聚合统计（按时间/科目/分心类型），SQLite 的 SQL 更合适。
- 单文件便于备份迁移。

### 4.5 不选的方案
- **Electron**：体积与内存过大，不适合常驻后台。
- **Flutter / React Native**：与"主用 Rust"冲突。
- **纯命令行**：需要可视化与系统托盘。
- **云端推理摄像头**：隐私不可接受。

### 关键设计点
1. **分层解耦**：UI 只发命令/订阅事件，不直接调用服务；服务通过 **trait 抽象**，便于单测与替换。
2. **事件总线**：计时器 tick、分心事件、提醒触发通过 `tokio::sync::broadcast` / `mpsc` 异步通信；前端通过 Tauri `listen` 订阅。
3. **Tauri Command 作为 API 边界**：所有业务能力暴露为 `#[tauri::command]`，前端通过 `invoke` 调用，禁止前端直接访问数据库。
4. **平台相关代码隔离**：`src/platform/{windows,macos,linux}/` 目录，核心逻辑平台无关。
5. **降级策略**：检测服务异常 → 退化为纯计时器；LLM 不可用 → 仅规则分析；无网 → 离线核心功能。
6. **隐私边界**：摄像头帧只进内存推理，不落盘、不上传；窗口标题仅本地匹配。
7. **账号与数据隔离**：多账号数据按 `user_id` 隔离；离线登录用本地缓存凭证。

## 6. 数据库设计（SQLite）

> 规范：表名 `snake_case` 复数；主键 `id INTEGER PRIMARY KEY AUTOINCREMENT`；时间戳 `INTEGER`（Unix 毫秒）；布尔 `INTEGER 0/1`；外键启用 `PRAGMA foreign_keys = ON`。

## 8. 迁移路线图（Dioxus 0.8 → Tauri 2）

### 8.1 总体策略
**先拆业务逻辑 → 再迁 UI → 最后补系统能力**

```
阶段1: 抽象层        阶段2: 新建骨架        阶段3: 迁移核心        阶段4: 补系统能力
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ Dioxus 0.8   │    │ Tauri 2      │    │ Tauri 2      │    │ Tauri 2      │
│ 现有代码     │ →  │ + 业务逻辑层 │ →  │ + 核心功能   │ →  │ + 完整能力   │
│              │    │ + 空白前端   │    │ + Web UI     │    │ (托盘/通知等)│
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

### 8.2 阶段详解

#### 阶段 1：抽象业务逻辑层（1–2 周）
**目标**：把 Dioxus 中与 UI 无关的业务逻辑拆为纯 Rust 库。

| 任务 | 产出 |
|---|---|
| 创建 `crates/tomatoclock-core/` workspace 成员 | 独立 crate |
| 迁移计时器状态机（开始/暂停/完成/放弃） | `timer/engine.rs` |
| 迁移分心判定规则（窗口/输入/摄像头） | `distraction/engine.rs` |
| 迁移统计聚合逻辑 | `stats/aggregator.rs` |
| 迁移规则型分析引擎 | `insights/rules.rs` |
| 迁移数据仓储（SQLite 操作层） | `storage/` |
| 所有逻辑**不依赖任何 UI 框架**，纯 Rust | 可通过单元测试验证 |

> **关键**：此阶段 Dioxus 仍可正常运行，只是把"胖 UI"拆成"薄 UI + 厚核心"。

#### 阶段 2：新建 Tauri 2 骨架（0.5–1 周）
**目标**：新建 Tauri 2 项目，接入 `tomatoclock-core`。

| 任务 | 产出 |
|---|---|
| `cargo create-tauri-app` 选择 Svelte/TS | 前端骨架 |
| 添加 `tomatoclock-core` 作为依赖 | `Cargo.toml` |
| 实现 `#[tauri::command]` 暴露核心能力 | `src-tauri/src/commands/` |
| 前端跑通一个最小页面（如"开始番茄"按钮） | 最小可用 |
| 配置托盘、通知插件 | `tauri.conf.json` |

#### 阶段 3：迁移核心功能（2–3 周）
**目标**：用 Web UI 重写核心页面，Dioxus 代码可废弃。

| 周次 | 任务 |
|---|---|
| W1 | 番茄计时器主界面 + 托盘显示剩余时间 |
| W2 | 学习记录（文本/图片/标签/科目）+ 任务管理 |
| W3 | 数据统计（趋势/分布/热力图）+ 规则型分析 |

#### 阶段 4：补系统能力（1–2 周）
**目标**：补齐 Dioxus 难以实现的系统级能力。

| 任务 | Tauri 插件/API |
|---|---|
| 系统托盘常驻 + 右键菜单 | `tauri-plugin-tray` |
| 桌面通知 | `tauri-plugin-notification` |
| 浮窗强提醒（最高级） | `WebviewWindow` + 置顶 |
| 全局快捷键（开始/暂停） | `tauri-plugin-global-shortcut` |
| 摄像头调用（Web 端） | `navigator.mediaDevices.getUserMedia` + Rust 端 ONNX 推理 |
| 语音提醒 | 系统 TTS 或 Web Speech API |

#### 阶段 5：验证与收尾（1 周）
| 任务 | 产出 |
|---|---|
| Windows 端完整测试 | 可用 demo |
| Dioxus 代码归档或删除 | 代码整洁 |
| 日志与错误处理完善 | 可观测性 |

### 8.3 并行工作建议
- **Rust 工程师**：聚焦阶段 1、2、4（业务逻辑 + Tauri 后端）
- **前端工程师**：聚焦阶段 3（Web UI）
- 若只有你一人：严格按阶段顺序做，阶段 1 是最大价值点

### 8.4 阶段 1 的代码示例（核心层抽象）

```rust
// crates/tomatoclock-core/src/timer/engine.rs
// 纯 Rust，不依赖任何 UI 框架

use std::time::Instant;

pub struct TimerEngine {
    state: TimerState,
    started_at: Option<Instant>,
    planned_duration: u64, // 秒
    accumulated: u64,
}

#[derive(Debug, Clone, PartialEq)]
pub enum TimerState {
    Idle,
    Running,
    Paused,
    Completed,
    Abandoned,
}

#[derive(Debug, Clone)]
pub struct TimerEvent {
    pub kind: TimerEventKind,
    pub remaining_seconds: u64,
}

#[derive(Debug, Clone)]
pub enum TimerEventKind {
    Tick,
    Completed,
    Paused,
    Resumed,
}

impl TimerEngine {
    pub fn new(planned_duration: u64) -> Self { ... }
    pub fn start(&mut self) { ... }
    pub fn pause(&mut self) { ... }
    pub fn resume(&mut self) { ... }
    pub fn tick(&mut self) -> Option<TimerEvent> { ... } // 每秒调用
    pub fn complete(&mut self) { ... }
    pub fn abandon(&mut self) { ... }
}
```

```rust
// Tauri 侧调用（src-tauri/src/commands/timer.rs）

#[tauri::command]
pub async fn start_timer(
    state: State<'_, TimerState>,
    duration: u64,
) -> Result<TimerStartResponse, String> {
    let mut engine = state.engine.lock().await;
    engine.start(duration);
    Ok(TimerStartResponse { ... })
}
```

| 风险 | 缓解 |

## 9. 给开发人员的落地建议

### 8.1 阶段划分
- **V1.0 MVP**：M1–M10（Windows），跑通核心闭环。
- **V1.1**：M11–M12 + macOS/Linux 适配 + 数据导入导出。
- **V1.2**：M13 LLM + M17 白噪音。
- **V2**：M14 多端同步 + M16 插件 + M18 移动端。

### 8.2 技术要点
1. **计时器**：`std::time::Instant` 单调时钟，避免系统时间调整；UI 每秒从事件总线拉取剩余时间。
2. **分心判定**：三种检测器各自产出"候选分心事件"，由**判定引擎**融合（如窗口 + 摄像头同时触发才升高级别）。
3. **渐进式提醒**：状态机实现，每级有冷却时间，避免重复轰炸。
4. **摄像头隐私**：推理在独立线程，帧数据不跨线程留存、不落盘；关闭摄像头即停止采集。
5. **离线优先**：所有网络能力（LLM/同步）封装为可选服务，不可用时优雅降级。
6. **平台隔离**：第一周建好 `src/platform/{windows,macos,linux}/` 目录，窗口/输入/摄像头各自适配。
7. **单测重点**：分心规则匹配、统计聚合、分析规则、计时器状态机——纯函数最易测。
8. **日志**：关键事件（番茄开始/结束、分心检测、提醒触发、LLM 调用）必须打结构化日志。

### 8.3 风险与缓解
| 风险 | 缓解 |
|---|---|
| 摄像头模型精度不足导致误判 | 多模态融合判定；灵敏度可调；用户可关闭摄像头仅用窗口/输入 |
| 跨平台窗口/输入 API 差异大 | 早期抽象 trait；Windows 先跑通，其他平台逐步适配 |
| LLM 费用与延迟 | 默认关闭；用户显式授权；本地缓存近期总结 |
| 常驻后台被系统杀进程 | 系统托盘保活；Windows 注册为后台任务 |
